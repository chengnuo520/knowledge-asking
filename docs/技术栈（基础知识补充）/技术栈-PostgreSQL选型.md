# 技术栈说明：为什么选 PostgreSQL 而不是 MySQL

> 适用：知识库 / RAG 类项目的数据层选型
> 结论先说：**不是"PG 比 MySQL 强"，而是"这个业务需要的能力，MySQL 给不了或者给得很别扭"**
> 本文结构：一、业务背景｜二、需求拆解｜三、本质差异｜四、逐项对比｜五、决策矩阵｜六、如果坚持 MySQL｜七、什么时候该换回去｜八、测试题

---

## 一、业务背景

先明确项目在做什么，否则选型讨论会变成空对空。

### 1.1 项目要存什么

这是一个「文档知识库 + 问答」系统，核心数据只有两类：

```
rag_documents（文档元信息）   1 ──── N   rag_chunks（分块）
  doc_id                            chunk_id
  name（唯一）                       doc_id（外键，级联删除）
  mime_type                         chunk_index
  size                              content           ← 块的原文
  content_hash（SHA-256）            embedding_text    ← 补了章节前缀的检索文本
  chunk_count（冗余计数）             outline_path      ← 章节路径，形如 ["保修政策","三、换货"]
  ingested_at                       embedding         ← 向量，vector(1024)
```

### 1.2 这个业务的数据特征

| 特征 | 具体表现 | 对数据库的要求 |
|---|---|---|
| **结构是树的** | 一个块要记住自己在「保修政策 › 三、换货 › 3.2 时限」 | 需要存**有序数组**，而不是拼字符串 |
| **写操作是整体替换** | 重新上传 = 删旧块 + 写文档 + 写新块 | 需要**事务**保证三步原子 |
| **读操作是批量** | 列表页展示 N 篇文档的块数、大小 | 需要聚合与排序 |
| **将来的检索是向量** | top-K 相似块召回 | 需要**向量类型 + 相似度索引** |
| **体量很小** | 目前 13 篇文档 / 18 个块；压力测试 19MB 文档 → 7143 块，入库 633ms | 性能不是瓶颈，**功能覆盖**才是 |

### 1.3 一句话的业务诉求

> 想用**一个数据库**同时解决「关系数据 + 数组结构 + 向量检索」，把系统复杂度压到最低。

这句诉求直接决定了选型——因为它排除了"关系库 + 专用向量库"的双写方案。

## 二、需求拆解：哪些是硬需求，哪些是偏好

选型吵架的根源，是把"偏好"当成了"硬需求"。所以先分级。

| 需求 | 等级 | 说明 |
|---|---|---|
| 事务保证（删旧块+写新块+改计数） | **硬需求** | 做不到就会产生"文档在、块丢了"的脏数据 |
| 存有序的章节路径 | **硬需求** | 拆成 JSON 字符串也能凑合，但每次读写都要序列化，且无法按路径过滤 |
| 向量类型 + 相似度检索 | **硬需求（下一阶段）** | 这是本项目存在的意义 |
| 唯一约束 + upsert | 硬需求 | 同名文档覆盖、幂等上传依赖它 |
| 外键级联删除 | 硬需求 | 删文档自动删块 |
| 中文全文检索 | 软需求 | 当前用不到（块数是几十量级，可以直接全表扫），但将来可能 |
| 极高并发写入 | 非需求 | 单机、个人/小团队场景 |
| 千万级向量 | 非需求 | 十万级以内 |

**关键判断**：前四条（事务、数组、向量、约束）都是"能自然表达"的诉求，而不是"能凑合实现"的诉求。MySQL 在前两条上能凑合，第三条上凑合不了。

## 三、本质差异：两种设计哲学

这不是"谁更快"的问题，而是两个数据库对"数据应该长什么样"的假设不同。

| 维度 | PostgreSQL | MySQL |
|---|---|---|
| **设计起点** | 对象-关系型：**数据库应该能表达复杂类型** | 关系型：**表就是行和列，保持简单** |
| **扩展方式** | 扩展机制（`CREATE EXTENSION`）：向量、JSONB、地理、分词都是扩展 | 存储引擎 / 插件，扩展能力受限 |
| **类型系统** | 数组、范围、枚举、复合类型、JSONB、自定义类型 | 基本标量 + JSON（8.0） |
| **事务** | DDL 也参与事务（迁移失败可整体回滚） | DDL 隐式提交，无法回滚 |
| **并发模型** | 进程/连接，MVCC | 线程/连接，MVCC（InnoDB） |
| **许可** | PostgreSQL License（宽松，类 MIT） | GPLv2 + 商业授权（闭源分发需注意） |

一句话总结这个差异：

> MySQL 假设"你把数据拍平成行和列"；PostgreSQL 允许"数据保持它本来的形状"。

本项目的章节路径，**本来就该是数组**。在 PG 里它就是数组；在 MySQL 里它必须被拍平成 JSON 或逗号分隔字符串，然后每次使用时再解析回来。这就是"表达力"的差别。

## 四、逐项对比（结合本项目）

### 4.1 向量检索（决定性因素）

| | PostgreSQL + pgvector | MySQL |
|---|---|---|
| 向量类型 | `vector(1024)` 是一等类型，可建索引 | 8.0 **没有**原生向量类型；新版本才引入 `VECTOR`，生态（驱动、ORM、工具链）远不成熟 |
| 相似度查询 | `ORDER BY embedding <=> ?::vector LIMIT 10`（余弦距离） | 需应用层算，或依赖外部向量库 |
| 索引 | HNSW / IVFFlat | 无对应能力 |
| 与业务数据同库 | ✅ 一个事务里既能查块又能算相似度 | ❌ 必须跨系统 |

本项目 `schema.sql` 的第一行就是：

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

**这不是偏好，是依赖**——没有这个扩展，`rag_chunks.embedding vector(1024)` 这一列根本建不出来，应用启动时就会失败（`spring.sql.init.mode=always` 会执行它）。

### 4.2 章节路径（最容易被忽略，但天天要用）

| | PostgreSQL | MySQL |
|---|---|---|
| 存法 | `outline_path TEXT[] NOT NULL DEFAULT '{}'` | `JSON` 或 `VARCHAR` 拼 `a/b/c` |
| 读出来 | 直接是 `String[]` | JSON 解析 / 字符串 split |
| 按路径过滤 | `WHERE '总则' = ANY(outline_path)` | JSON 函数或 `LIKE '%总则%'`（易误匹配） |
| 索引 | GIN 索引可加速数组包含查询 | 需函数索引，且语义弱 |

代码里的差别很直观：

```java
// PG：直接读写数组
new ChunkMetadata(readOutlinePath(rs, "outline_path"), sourceFile, Map.of());

// MySQL 方案：每次都要序列化/反序列化
String json = MAPPER.writeValueAsString(path);      // 写
List<String> path = MAPPER.readValue(json, LIST);   // 读
```

一个字段的差异不足以定选型，但它代表了**整条链路上反复出现的摩擦**：块、文档、将来可能的 `chunk_spec` 参数快照，都是结构化数据。

### 4.3 事务与一致性

两者都支持 ACID，差别在边界：

| 场景 | PostgreSQL | MySQL |
|---|---|---|
| 「删旧块 + 更新文档 + 写新块」 | ✅ 单事务，失败全回滚 | ✅ 同样支持（InnoDB） |
| 迁移脚本中途失败 | ✅ DDL 可回滚，库回到迁移前 | ❌ DDL 隐式提交，可能停在"表改了一半"的中间态 |
| `ON CONFLICT DO UPDATE`（upsert） | ✅ 语义清晰 | `ON DUPLICATE KEY UPDATE`，能用但语义偏"往唯一键上撞" |

两者在这一项上**打平**（除了 DDL），所以它不构成本项目的选型理由——这一点要诚实，很多文章把事务说成 PG 独有，是错的。

### 4.4 中文全文检索（软需求，但值得知道）

| | PostgreSQL | MySQL |
|---|---|---|
| 方案 | `zhparser` / `pg_jieba` 扩展，中文分词质量好 | 内置 `ngram` parser，可做二元切分 |
| 效果 | 可自定义词典、支持同义词 | 基本可用，细粒度控制弱 |

本项目目前没用到全文检索（块只有几十个，Python/Java 侧过滤足够），但**当块数上万、需要关键词召回时**，PG 的扩展生态会更从容。注意：这是"将来更从容"，不是"现在必需"。

### 4.5 性能（本项目不是瓶颈，但要讲清）

| 维度 | 说明 |
|---|---|
| 单条 CRUD | MySQL 略优（更简单的执行路径，团队也更熟悉调优） |
| 聚合/复杂查询 | PG 优化器更强（多表、CTE、窗口函数） |
| `COUNT(*)` | **两者都不快**（MVCC 都要扫可见行），所以本项目才用 `chunk_count` 冗余列 |
| 实测 | 19MB 文档 → 7143 块，入库 633ms；当前 13 篇文档的列表查询在毫秒级 |

**结论**：在这个数据量级上比较性能没有意义。真正该比较的是"能不能表达"。

### 4.6 运维、生态与团队

必须承认 MySQL 的优势：

| 维度 | 优势方 |
|---|---|
| 人才储备 / 招聘 | **MySQL**（国内更普及，运维更熟） |
| 云厂商托管 | 两者都有，MySQL 更便宜常见 |
| 图形化工具 | MySQL 生态更丰富（Navicat 等） |
| 容器化一条命令起库 | **PG**（官方镜像 + pgvector 镜像现成，`docker-compose.kb.yml` 就是） |
| 许可风险 | **PG**（宽松许可，无 GPL 传染问题） |
| 备份/主从 | 两者都成熟；PG 的 PITR 与逻辑复制更灵活 |

这一项 MySQL 在"人"的层面明显占优，PG 在"许可 + 扩展"上占优。

## 五、决策矩阵

按本项目的真实权重打分（1-5 分，权重来自第二部分的需求分级）：

| 维度 | 权重 | PostgreSQL | MySQL | 说明 |
|---|---|---|---|---|
| 向量检索能力 | 30% | 5 | 1 | 决定性项 |
| 结构表达（数组/JSON） | 15% | 5 | 3 | 数组 vs JSON |
| 事务一致性 | 20% | 5 | 4 | DDL 可回滚是加分 |
| 约束与级联 | 10% | 5 | 5 | 打平 |
| 运维与团队熟悉度 | 15% | 3 | 5 | MySQL 占优 |
| 许可与成本 | 5% | 5 | 3 | GPL vs 宽松许可 |
| 性能（本量级） | 5% | 4 | 4 | 都不构成瓶颈 |
| **加权总分** | | **4.70** | **2.95** | |

如果换一个业务（比如纯电商订单表、报表系统、团队只有 MySQL DBA），把"向量检索"权重降到 0、"团队熟悉度"提到 30%，结论会立刻反转成 MySQL。**选型是算出来的，不是背出来的。**

## 六、如果坚持用 MySQL，要付什么代价

这是答辩时最容易被追问的一点，必须能答。

### 6.1 方案 A：MySQL + 外部向量库（Milvus / Qdrant）

```
MySQL（文档与块）  ←→  向量库（embedding）
                 双写
```

代价：

1. **双写一致性**：写块成功、写向量失败，就会出现"块在库里但检索不到"。需要补偿任务或消息队列
2. **事务边界消失**：一个操作跨两个系统，无法用一个事务兜住
3. **运维翻倍**：两套存储、两套备份、两套监控
4. **删除要清理两处**：删文档必须同时删向量，否则留下"幽灵向量"，召回后查不到原文

### 6.2 方案 B：MySQL 8 + JSON 存向量，应用层算余弦

```sql
-- 只能这么存
embedding JSON   -- [0.013, -0.22, ...]
```

代价：每次检索要**把全表向量拉到内存算相似度**。一万个块 × 1024 维 = 一千万个浮点数，单次查询就是几百毫秒起步，且随数据量线性恶化。这不是"慢一点"，是**方案不可用**。

### 6.3 方案 C：MySQL 9 + VECTOR 类型

理论可行，但要面对：驱动与 ORM 支持不完整、索引能力与 pgvector 有差距、生产案例少。**用一个新特性去赌项目地基，风险不划算。**

## 七、什么时候该换回去

选型不是终身制，说清"什么时候该换"比"为什么选它"更显专业。

| 场景 | 该换成 |
|---|---|
| 项目退化成纯业务 CRUD，不再做检索 | **MySQL 完全够用**，且团队更熟 |
| 向量规模上千万、检索 QPS 很高 | **专用向量库**（Milvus/Qdrant）+ PG 存业务数据 |
| 需要极简运维、托管成本敏感、无向量需求 | **MySQL**（云厂商托管便宜） |
| 需要复杂分析、窗口函数、地理、JSONB 深查询 | **PG**（本来就是强项） |

本项目的边界很清楚：**只要还做 RAG，PG 就是那个"一个库解决问题"的最低成本方案**；一旦不做检索了，它就变成了过度设计。

## 八、测试题

### 8.1 基础自检

<details>
<summary><b>Q1. 一句话说明本项目为什么用 PG？</b></summary>
<p>因为需要「关系数据 + 数组 + 向量」同库共存：章节路径用 <code>TEXT[]</code>、向量用 <code>vector(1024)</code>、文档与块的强一致用事务兜住。MySQL 在向量这一项上无法自然表达。</p>
</details>

<details>
<summary><b>Q2. 如果没有向量需求，还会选 PG 吗？</b></summary>
<p>不一定。纯业务 CRUD + 团队只有 MySQL 经验时，MySQL 更划算——它的生态、人才、托管成本都占优。选型的答案是随需求变的。</p>
</details>

<details>
<summary><b>Q3. <code>outline_path</code> 为什么不用 JSON 存？</b></summary>
<p>它本质是<strong>有序数组</strong>，不是键值对象。JSON 每次读写要序列化，按路径过滤要写 JSON 函数，<code>LIKE</code> 又容易误匹配；PG 的 <code>TEXT[]</code> + <code>GIN</code> 索引是原生支持。</p>
</details>

<details>
<summary><b>Q4. PG 的事务比 MySQL 强在哪？</b></summary>
<p>强在 <strong>DDL</strong>：迁移脚本中途失败时，PG 能把整个迁移回滚；MySQL 的 DDL 会隐式提交，可能停在&quot;表改了一半&quot;的状态。DML 事务两者都支持。</p>
</details>

<details>
<summary><b>Q5. 两边 <code>COUNT(*)</code> 都快吗？</b></summary>
<p>都不快。MVCC 下都要扫描可见行，所以本项目用 <code>chunk_count</code> 冗余列，并在块级增删后同事务重算——这是业务层的优化，不是选型的理由。</p>
</details>

<details>
<summary><b>Q6. 为什么不用「MySQL + Milvus」？</b></summary>
<p>双写一致性无法用事务保证，删文档要清两处，运维成本翻倍。在十万级向量、单机部署的场景下，引入第二个存储系统的复杂度远大于收益。</p>
</details>

### 8.2 面试延伸

<details>
<summary><b>Q7. pgvector 的 HNSW 和 IVFFlat 怎么选？</b></summary>
<p>IVFFlat 建索引快、内存占用小，但召回率受 <code>lists</code> 与探测数影响，适合数据量大且可接受少量漏召；HNSW 召回率高、查询快，但建索引慢、内存占用大。数据还会持续增长、且要求召回质量时优先 HNSW；一次性导入的历史数据可用 IVFFlat。</p>
</details>

<details>
<summary><b>Q8. PG 是进程模型，高并发连接会有什么问题？怎么解？</b></summary>
<p>每个连接一个后端进程，内存开销约几 MB 到十几 MB，几百连接就会吃满内存。解法是连接池（PgBouncer / HikariCP），把并发连接数压到 CPU 核数量级。本项目 Hikari 默认 10 个连接，完全够用。</p>
</details>

<details>
<summary><b>Q9. 如果向量规模真的涨到千万级，PG 还撑得住吗？</b></summary>
<p>撑得住但不再是优解。此时通常拆成：PG 存业务数据 + 专用向量库存 embedding，用消息队列做最终一致。判断标准是&quot;检索延迟是否成为体验瓶颈&quot;，而不是&quot;数据量到某个数字&quot;。</p>
</details>

<details>
<summary><b>Q10. 你项目里的 upsert 是怎么做的？两个库语义有差别吗？</b></summary>
<p><code>INSERT ... ON CONFLICT (doc_id) DO UPDATE SET ...</code>。MySQL 对应 <code>ON DUPLICATE KEY UPDATE</code>，能力相当；差别在 PG 可以指定<strong>冲突目标</strong>（哪个唯一约束），MySQL 是对任意唯一键生效，语义更粗。</p>
</details>

<details>
<summary><b>Q11. GPLv2 许可对商业项目意味着什么？</b></summary>
<p>MySQL 社区版是 GPLv2：如果分发包含 MySQL 的软件，可能被要求开源；不分发（SaaS 自用）通常没问题，但闭源分发要买商业授权。PostgreSQL License 是宽松许可，无此约束。这是企业选型时会认真算的一项。</p>
</details>

<details>
<summary><b>Q12. 如果让你重新设计这个知识库的表结构，会改什么？</b></summary>
<p>三点：① 加 <code>chunk_spec jsonb</code> 记录每篇文档用的分块参数（可追溯）；② <code>rag_chunks</code> 加 <code>enabled</code> 支持块级屏蔽；③ 加 <code>knowledge_base</code> 表做多库隔离，<code>rag_documents</code> 挂 <code>kb_id</code> 外键。这三项都不影响当前选型，但都会让 PG 的 JSONB 与约束能力更值钱。</p>
</details>
