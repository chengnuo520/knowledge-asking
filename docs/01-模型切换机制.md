# 模型切换机制

> 一句话：把模型的所有连接信息折叠成一个 **id 字符串**，工厂负责把 id 展开成完整的模型实例。
>
> 文档结构：一、业务目标｜二、理论知识｜三、实践操作｜四、测试题（1~5 层追问）

---

## 一、业务目标

### 1.1 场景

同一个问答界面，背后可能接三种完全不同的模型：

| 模型 | 来源 | 特点 |
|---|---|---|
| `remote-deepseek` | DeepSeek 云 API | 联网、质量高、按量计费 |
| `ollama-deepseek-r1` | 本机 Ollama | 断网可用、免费、有推理过程 |
| `ollama-qwen3-vl` | 本机 Ollama | 支持看图（Vision） |

使用者需要在界面上随时切换，用于对比回答质量、在没网时继续工作、或者验证某个模型的能力边界。

### 1.2 痛点（做之前是什么样）

迁移前的 Spring AI 版本，模型是**写死在代码里**的：

- 换一个模型 = 改 Java 代码 → 重新编译 → 重启服务
- 想临时对比两个模型？做不到，只能改代码
- 每加一个模型，都要在 Controller 里加分支

### 1.3 目标（可验收）

| # | 目标 | 验收标准 |
|---|---|---|
| 1 | 新增模型零代码 | 只在 `application.yml` 追加 5 行，重启即可用 |
| 2 | 运行时切换 | 前端下拉选择，同一个接口用不同模型返回 |
| 3 | 不重复创建 | 同一模型多次请求只实例化一次（缓存命中） |
| 4 | 未知模型有明确错误 | 传不存在的 id 返回可读错误，而不是空指针 |

### 1.4 范围边界（明确不做什么）

- ❌ 不做**自动路由**（按问题难度选模型）
- ❌ 不做**负载均衡/降级**（远程失败自动切本地）
- ❌ 不做**密钥管理**（密钥来自环境变量，不落库）
- ❌ 不做**用量统计与计费**

这些都属于"模型治理"，是后续阶段的事。本功能只解决"**用哪个模型，由谁说了算**"。

## 二、理论知识

### 2.1 为什么把模型压缩成一个 id

一个模型实例需要三个参数：`baseUrl` + `apiKey` + `modelName`。

如果让前端把这四个字段（连 id）都传上来，会有三个问题：

1. **前端知道得太多**：API Key 绝不能出现在浏览器
2. **接口不稳定**：每加一个模型，前端 payload 就要变
3. **无法校验**：用户能传任意 baseUrl，等于给了他把请求打到任何地方的能力

所以接口只收一个 `id`，**id 是白名单**——只有配置里存在的 id 才被接受：

```json
POST /api/chat
{ "message": "你好", "model": "ollama-qwen3-vl" }
```

这是"**用标识符代替资源本身**"的经典做法，和 REST 里传 `userId` 而不是整个 user 对象是同一个道理。

### 2.2 AgentScope 的两层结构：Model 与 Agent

这是理解本项目最关键的一点：

| 层 | 类 | 职责 |
|---|---|---|
| 模型层 | `OpenAIChatModel` | 只负责"连接 + 一次推理请求"：baseUrl、apiKey、modelName、temperature |
| 代理层 | `ReActAgent` | 负责"推理循环"：多轮、工具调用、消息历史，把 Model 包起来用 |

```java
OpenAIChatModel model = factory.getOrCreate(modelId);          // 连接信息
try (ReActAgent agent = ReActAgent.builder()                   // 执行单元
        .name("assistant").model(model).build()) {
    String reply = agent.call(msg).block().getTextContent();
}
```

**为什么要多这一层？** 因为 Model 只能"一问一答"，而 Agent 能在中间插入工具调用、反思、多轮修正。本项目现在是单轮问答，看起来这层多余；但一旦接上工具（查天气、查数据库），Agent 就是必须的载体。

### 2.3 OpenAI 兼容协议：为什么一个类能连两家

`OpenAIChatModel` 只认协议，不认厂商。DeepSeek 和 Ollama 都提供 OpenAI 兼容端点：

```
baseUrl=https://api.deepseek.com/v1        → POST .../v1/chat/completions
baseUrl=http://localhost:11434/v1          → POST .../v1/chat/completions
```

同一个类、同一套请求体、同一个响应结构。**这是整个方案能成立的前提**——如果没有这个行业事实上的统一协议，就得为每家写一个适配器。

> 注意：`baseUrl` 必须写到 `/v1` 层级。AgentScope 只会在其后拼 `/chat/completions`，**不会自动补 `/v1`**。这是本项目第一个坑。

### 2.4 工厂 + 缓存：为什么不是每次 new

```java
private final Map<String, OpenAIChatModel> cache = new ConcurrentHashMap<>();

return cache.computeIfAbsent(modelId, id -> OpenAIChatModel.builder()...build());
```

三个理由：

| 理由 | 说明 |
|---|---|
| **复用底层资源** | `OpenAIChatModel` 内部持有 HTTP 客户端与连接池，反复 new 会泄漏连接 |
| **线程安全** | `ConcurrentHashMap.computeIfAbsent` 保证并发下"只创建一次"，即使 10 个请求同时进来 |
| **懒加载** | 只有真正被用到的模型才创建；配置里写了 3 个，用户只用 1 个，就只建 1 个 |

对比一下常见错误写法：

```java
// ❌ 每次请求都 new —— 连接池泄漏、性能差
return OpenAIChatModel.builder().apiKey(...).build();

// ❌ 先查再放 —— 并发下可能创建两次
if (!cache.containsKey(id)) { cache.put(id, build()); }

// ✅ 原子的 computeIfAbsent
return cache.computeIfAbsent(id, this::build);
```

### 2.5 `@ConfigurationProperties` 做了什么事

```java
@Bean
@ConfigurationProperties(prefix = "chat")
public ChatProperties chatProperties() { return new ChatProperties(); }
```

它把 yml 的结构**按名字**映射成 Java 对象：

```yaml
chat:
  models:                    # → ChatProperties.models
    - id: remote-deepseek    # → ModelDefinition.id
      base-url: ...          # → ModelDefinition.baseUrl（连字符自动转驼峰）
```

两个容易忽略的点：

- **松散绑定**：`base-url` / `baseUrl` / `base_url` 都能绑定到 `baseUrl`
- **不校验**：配置写错了（比如漏了 `api-key`）启动不报错，只有真正调用时才炸。要提前发现，需要加 `@Validated` + `@NotBlank`

### 2.6 方案对比：自动装配 vs 手动构建

| | Spring AI（迁移前） | 本项目（AgentScope） |
|---|---|---|
| 模型创建 | 自动装配，注入 `ChatModel` 即可 | 必须手动 `builder()` |
| 多模型 | 每个模型一个 `@Bean`，或靠 `@Qualifier` | 一个工厂按 id 取，天然支持 N 个 |
| 配置驱动 | 需自己写条件装配 | 配置列表 + 工厂，天然配置驱动 |
| 换框架成本 | 低（生态成熟） | 中（文档少，需读源码） |

AgentScope 没有 Spring 的自动装配生态，看似是缺点，但**对本项目反而是优点**：模型创建完全由我们控制，多模型切换不需要和框架的装配规则搏斗。

### 3.3 Step 3：工厂（核心 40 行）

```java
@Component
public class ChatModelFactory {

    private final List<ModelDefinition> definitions;
    private final Map<String, OpenAIChatModel> cache = new ConcurrentHashMap<>();

    public ChatModelFactory(List<ModelDefinition> definitions) {
        this.definitions = definitions;
    }

    public OpenAIChatModel getOrCreate(String modelId) {
        ModelDefinition def = definitions.stream()
                .filter(m -> m.getId().equals(modelId))
                .findFirst()
                .orElseThrow(() -> new IllegalArgumentException("未知模型: " + modelId));

        return cache.computeIfAbsent(modelId, id -> {
            String apiKey = def.getApiKey() == null || def.getApiKey().isBlank()
                    ? "ollama" : def.getApiKey();
            return OpenAIChatModel.builder()
                    .apiKey(apiKey)
                    .baseUrl(def.getBaseUrl())
                    .modelName(def.getModelName())
                    .stream(false)
                    .build();
        });
    }

    /** 供前端下拉框使用 */
    public List<ModelDefinition> listAll() { return definitions; }
}
```

### 3.4 Step 4：Controller 接收 id

```java
@PostMapping("/chat")
public Map<String, String> chat(@RequestBody Map<String, String> body) {
    String modelId = body.getOrDefault("model", "remote-deepseek");
    OpenAIChatModel model = factory.getOrCreate(modelId);

    try (ReActAgent agent = ReActAgent.builder().name("assistant").model(model).build()) {
        Msg msg = Msg.builder()
                .role(MsgRole.USER)
                .textContent(body.get("message"))
                .build();
        String reply = agent.call(msg).block().getTextContent();
        return Map.of("reply", reply == null ? "" : reply);
    }
}
```

同时暴露一个列表接口给前端渲染下拉框：

```java
@GetMapping("/models")
public List<Map<String, String>> models() {
    return factory.listAll().stream()
            .map(d -> Map.of("id", d.getId(), "name", d.getName()))
            .toList();
}
```

### 3.7 踩坑记录

| 坑 | 现象 | 原因 / 解法 |
|---|---|---|
| base-url 缺 `/v1` | 404 Not Found | AgentScope 只在 baseUrl 后拼 `/chat/completions`，不补 `/v1` |
| 以为框架会自动读配置 | 配置写了但不生效 | AgentScope 没有 Spring 自动装配，`chat.models` 是我们自己的配置 |
| `agent.call()` 拿到 null | 空指针 | 返回 `Mono<Msg>`，必须 `.block()` 再 `.getTextContent()` |
| 每次请求内存上涨 | 连接泄漏 | 忘了用工厂缓存，每请求 new 了 `OpenAIChatModel` |
| Ollama 报 apiKey 为空 | 400 | 本地模型要给个 dummy 值（本项目用 `"ollama"`） |

### Q1｜这套机制的核心抽象是什么？

<details>
<summary>参考答案 + 5 层追问</summary>
<p><strong>参考答</strong>：把模型的连接信息（baseUrl + apiKey + modelName）折叠成一个 id，接口只传 id，工厂按 id 展开实例。</p><blockquote><p><strong>L1 追问</strong>：为什么不让前端直接传 baseUrl？<br>要点：安全（Key 不能进浏览器、不能让用户指定任意地址）、稳定（接口不随模型数量变化）、可校验（id 就是白名单）。</p></blockquote><blockquote><p><strong>L2 追问</strong>：如果前端传了一个配置里没有的 id，会发生什么？你怎么设计这个错误？<br>要点：工厂 <code>findFirst().orElseThrow</code> 抛 <code>IllegalArgumentException</code>；Controller 统一转成 <code>{&quot;error&quot;:&quot;未知模型: xxx&quot;}</code> 的 400。不能返回 500，也不能静默用默认模型——后者会让用户以为切换成功了。</p></blockquote><blockquote><p><strong>L3 追问</strong>：想让&quot;传错 id 就用默认模型&quot;可以吗？利弊是什么？<br>要点：可以做（兜底更友好），但会<strong>掩盖调用方的错误</strong>——前端拼错 id 时永远发现不了。生产上更好的做法是显式报错 + 前端只从 <code>/api/models</code> 取选项，从源头避免非法值。</p></blockquote><blockquote><p><strong>L4 追问</strong>：如果模型配置要支持热更新（不重启就生效），你会怎么改？<br>要点：把 <code>List&lt;ModelDefinition&gt;</code> 换成可刷新的配置源（Nacos / 数据库 / 文件监听），工厂缓存加版本号或按需失效；难点在&quot;已创建的模型实例要不要重建&quot;——如果 Key 变了，必须重建，所以缓存 key 应带上配置版本。</p></blockquote><blockquote><p><strong>L5 追问</strong>：那如果没有 Nacos 这种配置中心，只有一个 yml，怎么做最简热更新？<br>要点：监听文件变更（<code>WatchService</code>）→ 重载配置 → 清空 <code>cache</code>。代价是短暂重建、需处理解析失败时保留旧配置。核心是<strong>缓存必须能被主动失效</strong>，否则永远只能靠重启。</p></blockquote>
</details>

### Q2｜为什么要有 `ReActAgent` 这一层？直接用 Model 不行吗？

<details>
<summary>参考答案 + 5 层追问</summary>
<p><strong>参考答</strong>：Model 只能&quot;一问一答&quot;，Agent 负责推理循环与工具调用。现在单轮问答看起来多余，但接工具时必须要它。</p><blockquote><p><strong>L1 追问</strong>：Agent 和 Model 分别持有哪类状态？<br>要点：Model 持有连接与参数（无对话状态）；Agent 持有一次会话的执行上下文（消息、迭代次数、工具列表）。</p></blockquote><blockquote><p><strong>L2 追问</strong>：为什么 Agent 要用 try-with-resources？<br>要点：<code>ReActAgent</code> 持有底层资源，需 <code>close()</code> 释放；不关会泄漏。</p></blockquote><blockquote><p><strong>L3 追问</strong>：一次请求 new 一个 Agent，那多轮对话的记忆存在哪？<br>要点：现在没有记忆——每轮都是新 Agent、新消息，所以问&quot;那第二个呢&quot;会失忆。要做多轮，需要会话级的 Agent 或外部 memory 组件，把历史消息带上。</p></blockquote><blockquote><p><strong>L4 追问</strong>：如果要支持工具调用，链路会怎么变？<br>要点：<code>ReActAgent.builder().tools(...)</code>，Agent 进入&quot;思考 → 调工具 → 观察 → 再思考&quot;循环；需要设置最大迭代次数防死循环，还要给工具加超时与权限。</p></blockquote><blockquote><p><strong>L5 追问</strong>：工具调用失败时，你希望 Agent 重试还是直接报错？怎么控制？<br>要点：区分可重试（网络超时）与不可重试（参数错误）；用最大重试次数 + 退避，并在迭代上限内收敛。关键是把&quot;失败原因&quot;作为观察结果喂回模型，让它自己改参数重试，而不是框架盲目重试。</p></blockquote>
</details>

### Q3｜缓存为什么用 `ConcurrentHashMap.computeIfAbsent`？

<details>
<summary>参考答案 + 5 层追问</summary>
<p><strong>参考答</strong>：保证并发下只创建一次，且线程安全。</p><blockquote><p><strong>L1 追问</strong>：<code>containsKey</code> + <code>put</code> 有什么问题？<br>要点：非原子。两个线程同时判断&quot;不存在&quot;，会各创建一次，后写的覆盖先写的，且前者创建的对象泄漏。</p></blockquote><blockquote><p><strong>L2 追问</strong>：<code>computeIfAbsent</code> 在什么情况下会退化？有没有坑？<br>要点：① mapping 函数里做耗时操作会<strong>锁住该桶</strong>，阻塞同桶其他 key；② mapping 函数里<strong>不能递归修改同一个 map</strong>（会死锁/并发异常）。所以建实例耗时长的场景，可考虑 double-check + 局部锁。</p></blockquote><blockquote><p><strong>L3 追问</strong>：如果模型配置变了，缓存怎么失效？<br>要点：现在不会失效（只能重启）。要支持就得显式 <code>cache.remove(id)</code> 或整体 <code>clear()</code>，并把配置版本纳入 key。</p></blockquote><blockquote><p><strong>L4 追问</strong>：缓存会不会无限增长？怎么控制？<br>要点：key 的数量 = 配置里的模型数（有限），所以理论上安全。但如果将来支持用户自定义模型，就要加上限 + LRU 淘汰。</p></blockquote><blockquote><p><strong>L5 追问</strong>：多实例部署时，这个缓存有意义吗？会有什么问题？<br>要点：每台机器各存一份，浪费但无害（实例创建便宜）。真正的问题是<strong>配置不一致</strong>——不同实例读到的配置版本不同，会出现&quot;同一请求打到不同机器行为不同&quot;，需要配置中心统一推送。</p></blockquote>
</details>

### Q4｜`@ConfigurationProperties` 和 `@Value` 有什么区别？为什么选前者？

<details>
<summary>参考答案 + 5 层追问</summary>
<p><strong>参考答</strong>：前者面向&quot;结构化配置&quot;，后者面向&quot;单个值&quot;。</p><blockquote><p><strong>L1 追问</strong>：松散绑定具体指什么？<br>要点：<code>base-url</code> / <code>baseUrl</code> / <code>base_url</code> 都能绑到 <code>baseUrl</code>，不用写一堆 <code>@Value(&quot;${chat.models[0].base-url}&quot;)</code>。</p></blockquote><blockquote><p><strong>L2 追问</strong>：配置写错了（比如漏了 api-key），启动会报错吗？<br>要点：不会。默认不校验。要提前暴露需加 <code>@Validated</code> + <code>@NotBlank</code>，否则只有调用时才炸。</p></blockquote><blockquote><p><strong>L3 追问</strong>：如果给 <code>modelDefinitions</code> 这个 Bean 加了 <code>@Validated</code>，能校验到列表里的元素吗？<br>要点：需要在 <code>List&lt;@Valid ModelDefinition&gt;</code> 上加元素级校验（<code>@Valid</code>），只在外层加不生效。</p></blockquote><blockquote><p><strong>L4 追问</strong>：配置里同一个 id 出现两次会怎样？<br>要点：<code>findFirst</code> 会取第一个，第二个被静默忽略——这是隐患。正确做法是启动时校验 id 唯一，重复直接失败（fail fast）。</p></blockquote><blockquote><p><strong>L5 追问</strong>：这属于什么类型的问题？怎么系统性防住？<br>要点：属于&quot;配置错误静默降级&quot;。系统性防守是三件事：启动期校验（唯一性、必填、枚举）、健康检查暴露配置摘要、以及配置变更后的冒烟测试。</p></blockquote>
</details>

### Q5｜这套设计有哪些边界？线上会出什么问题？

<details>
<summary>参考答案 + 5 层追问</summary>
<p><strong>参考答</strong>：单机、无路由、无降级、无熔断。</p><blockquote><p><strong>L1 追问</strong>：远程模型超时会怎样？<br>要点：请求一直挂着直到 HTTP 超时（Axios/HTTP 客户端默认可能很长），用户体验是&quot;转圈&quot;。需要设连接/读取超时。</p></blockquote><blockquote><p><strong>L2 追问</strong>：远程挂了，能不能自动切到本地？<br>要点：可以做降级，但要明确&quot;降级后回答质量不同&quot;，且要能告知用户。技术上在工厂外面包一层 fallback 逻辑即可。</p></blockquote><blockquote><p><strong>L3 追问</strong>：多个用户同时用同一个模型，会互相影响吗？<br>要点：模型实例是单例共享的（连接池共享），本身无状态，不会串话；但 QPS 高时会争抢连接，需要限流（本项目已有 60 次/分）。</p></blockquote><blockquote><p><strong>L4 追问</strong>：怎么统计每个模型花了多少钱？<br>要点：在 Agent 调用后取 usage（prompt/completion tokens），按模型单价累加；需要把 usage 从响应里透出来（现在被丢弃了）。</p></blockquote><blockquote><p><strong>L5 追问</strong>：如果要做&quot;按用户配额扣费&quot;，链路要怎么改？<br>要点：请求进入时校验配额 → 调用后按 usage 扣减 → 失败/超时不扣或退补。难点在于<strong>幂等</strong>（重试不能重复扣）与<strong>并发</strong>（同一用户并发请求要原子扣减）。</p></blockquote>
</details>

### Q6｜如果让你重构，你会改什么？

<details>
<summary>参考答案 + 5 层追问</summary>
<p><strong>参考答</strong>：加超时与校验、透出 usage、把缓存做成可失效。</p><blockquote><p><strong>L1 追问</strong>：最该先改哪一项？<br>要点：<strong>超时</strong>。没有超时的外部调用是线上事故的头号来源，且改动最小、收益最大。</p></blockquote><blockquote><p><strong>L2 追问</strong>：为什么不是先加多轮记忆？<br>要点：记忆是功能增量，超时是稳定性底线；底线问题优先级永远高于增量功能。</p></blockquote><blockquote><p><strong>L3 追问</strong>：加超时会带来什么新问题？<br>要点：超时时间设太短会误杀慢模型（推理模型本来就慢）；需要按模型区分超时，并给用户明确的&quot;超时&quot;提示而非&quot;失败&quot;。</p></blockquote><blockquote><p><strong>L4 追问</strong>：怎么验证超时真的生效了？<br>要点：用桩服务模拟挂起（sleep 30s），观察请求在 N 秒后返回超时错误；同时确认线程/连接被释放（不能有堆积）。</p></blockquote><blockquote><p><strong>L5 追问</strong>：如果超时后模型其实已经把结果算完并计费了，怎么办？<br>要点：这是&quot;超时≠未执行&quot;的经典问题。只能通过<strong>幂等键 + 结果回查</strong>（如果厂商支持）或接受损失；因此超时值要基于 P99 时延设定，而不是拍脑袋。</p></blockquote>
</details>
